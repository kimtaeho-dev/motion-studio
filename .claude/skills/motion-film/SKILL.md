# motion-film

디자이너는 코드를 몰라도 된다. 말로 요청하면 이 파이프라인을 돌리고, 게이트마다 확인을 받는다. 혼자 오래 다듬지 않고 첫 결과부터 보여 준다.
규칙은 레포 루트 `CLAUDE.md`가 우선한다. 단계가 바뀔 때마다 `node tools/state.mjs films/<이름> stage=<단계>`로 기록한다(앱의 진행 단계 표시와 승인 버튼이 이걸 본다).

## 0. 필름 준비
- `films/<이름>/`이 없으면 `node tools/new.mjs <이름>`.
- 디자이너가 레퍼런스(이미지, 영상)나 3D 모델(.glb)을 줬으면 `films/<이름>/refs/`에 둔다.

## 1. 입력 받기 (brief.md)
먼저 스타일(UI·프로덕트 모션 / 일러스트·손그림 / 타이포 / 제품 3D …)을 정한다 — 요청에 드러나면 묻지 않는다. UI 기본값(CLAUDE.md 룩)은 UI·프로덕트 모션일 때만 따르고, 다른 스타일이면 그 스타일의 문법으로 `<direction>`을 쓴다. 레퍼런스가 없다고 단순하게 줄이지 않는다.
`prompts/spec-template.md`의 `<inputs>` 항목 중 결과를 크게 바꾸는 빈 것을 한 번에 묻는다(4개까지, 나머지는 기본값으로 정해 브리프에 적는다).
`node tools/ask.mjs`로 묻는다. 질문마다 선택지 2~4개를 주고 권장안을 `--rec`으로 표시한다
(예: `--q "어디에 올리나요?" --opt "인스타 릴스 9x16" --opt "유튜브 16x9" --rec 1`). 고를 수 없는 것(제품 URL, 문구)은 선택지 없이 `--q`만.
앱이 선택지 카드로 보여준다. 채팅에는 질문을 다시 쓰지 않고 한 줄로만 알리고 턴을 끝낸다. 답이 오면 `brief.md`에 채운다.
실제 프로덕트 화면이 필요하면 디자이너에게 스크린샷을 달라고 한다(채팅창에 끌어다 놓으면 refs/에 저장된다). 프로덕트 UI를 상상으로 그리지 않는다.
브리프·숏리스트 단계에서는 `lib/`·`prompts/api.md`·`prompts/3d.md`·샘플 코드를 읽지 않는다 (구현 단계에서 읽는다 — 먼저 읽으면 이후 모든 단계에서 그만큼 비용이 든다).

## 2. 레퍼런스 → style_guide.md (있을 때만)
`prompts/reference.md` 절차. 문법만 가져오고 내용은 가져오지 않는다.

## 3. 숏리스트 → 디자이너 OK
`films/<이름>/shotlist.md`에 비트 그리드 표를 쓴다:

| 비트 | 시각 | 상태 | 커서 |
|---|---|---|---|

편집에서 얹을 곡이 정해져 있으면 먼저 디자이너에게 그 곡의 BPM과 첫 다운비트 시각(초)을 묻고 `bpm`·`beatOffset`으로 쓴다. 비트를 자동으로 측정하지 않는다.
다 쓰면 `node tools/state.mjs films/<이름> stage=shotlist waiting=approval`, 채팅에 표를 보여주고 승인을 부탁한 뒤 턴을 끝낸다.
**승인(앱의 승인 버튼 또는 채팅의 분명한 OK) 전에는 코드를 쓰지 않는다.**

## 4. 구현
`films/<이름>/film.json`(데이터)과 `films/<이름>/index.html`(코드). API는 `prompts/api.md`를 본다(`lib/` 소스를 통째로 읽지 않는다).
- `index.html` 맨 위 주석에 **장면 의도**를 남긴다: 비트마다 무엇이 왜 움직이는지 한 줄씩(timeline 키로). 수정 요청이 오면 코드보다 이 주석과 상태 표를 먼저 본다.
UI 모션 2D 필름은 `examples/sample-morph/`를 구조 참고로 읽는다(film.json의 params·timeline, index.html의 STATES 표, CUR 커서 키, 상태별 draw 함수). 3D·물리 필름은 `prompts/3d.md`를 읽는다(뼈대 포함 — 샘플은 막힐 때만). 프리셋에 없는 화풍(손그림·툰·종이·질감)은 THREE·캔버스로 직접 짠다 — 막히면 `examples/sample-crayon/`.
- 방법은 자유, 결과는 검사로: 렌더 계약(t의 순수 함수, rng, film.T)만 지키면 어떤 기법이든 쓴다. 아래 목록은 UI 모션의 기본 도구다.
- 숏리스트의 장면 시각은 `film.json` `timeline`에 이름을 붙여 옮기고, 코드에서는 `film.T.<이름>`으로만 쓴다.
- 화면에 나오는 문구, 포인트 컬러, 배경색은 `params`로 뺀다. `label`은 디자이너가 알아볼 한국어로.
- 움직임의 느낌(튀는 정도, 흔들림, 속도, 머무는 시간, 물결·입자 세기)은 **느낌 손잡이** 3~5개로 연다: `{ "type": "number", "value": 1, "min": 0, "max": 2, "step": 0.05, "label": "튀는 정도" }` → 속성 패널 슬라이더. 1 = 지금 그대로인 배율로 코드에서 곱한다(`prompts/api.md`).
- 컨테이너 크기/모서리/색/카메라: `loopTrack` (루프 아니면 `track`)
- 커서: 화면 좌표 키, UI를 가리킬 땐 그 시점 줌을 곱한다. 클릭은 카메라가 멈춘 뒤.
- 상태 안 내용: `swapAlpha` + `swapBlur`
- 인디케이터/노브: `stretch`
- 소리는 만들지 않는다 (CLAUDE.md, 소리와 템포)
- 3D(기기 목업, 제품 모델, 입체 글자, 재질 도형)·물리는 `prompts/3d.md`의 규칙과 뼈대대로. 포맷별 배치 표 + `W.fit`, 화면 속 UI는 `screen().draw`에서 2D로, 물체는 이름을 붙여 `W.add({ 이름: obj })`. 줄 세우기는 `row()`, 떨어뜨리기는 `pos: 'above'` + `land: { at: 비트 }`. 좌표를 손으로 계산하지 않는다.

## 5. 첫 결과 → 보여 주기
`stage=draft`. 다듬기 전에 디자이너에게 보여 준다(CLAUDE.md 작업 순서 4·6번).
- `node tools/render.mjs films/<이름> --check` — **막는 것**(필름이 안 뜸·렌더 오류·렌더 계약 위반·결정성)만 고친다. 구도·여백·정지·루프 이음새·`--check3d`의 겹침은 고치지 않고 메모로 남긴다(의도한 것은 `Stage.allow`로 표시).
- `--stills beats` → `contact-beats.png`를 한 번 열어 **깨진 것**(빈 화면, 화면 밖 주인공, 못 읽는 글자, 브리프와 다른 화풍)만 고친다.
- `--draft` 렌더 → 채팅에 초안이 플레이어에 있다는 것, 느낌 손잡이(무엇을 바꾸는지 한 줄씩), 다음에 다듬을 곳 2~3줄, 검사 메모. `node tools/state.mjs films/<이름> waiting=review` 후 턴을 끝낸다.
- 한 턴에 고치기 → 렌더 → 보기 순환은 2번까지. 막히면 더 파지 말고 고친 데까지 보여 준다.

## 6. 다듬기 (디자이너 의견 한 번 = 한 라운드)
`stage=critique round=<N>`. 디자이너가 짚은 것과, 내 제안 중 디자이너가 고른 것만 고친다 → `--from/--to`로 확인 → `--draft` → 5번처럼 보여 주고 `waiting=review`. `review_log.md`에 `## 라운드 N` 아래 요청과 고친 점.
`quality`가 `launch`면 보여 주기 전에 한 번 `node tools/critique.mjs films/<이름> <포맷> <가장 빠른 동작 시각>` → `/motion-critique` 채점, 점수를 메모에 붙인다(점수를 올리려고 혼자 더 돌지 않는다).

## 7. 전달 (디자이너가 OK하면)
- 요청된 포맷 전부 풀 렌더 (`--all-formats` 또는 `--format`). 포맷마다 `--check --format <포맷>`에 막는 것이 없어야 한다.
- 포스터: `node tools/render.mjs films/<이름> --stills <가장 좋은 시각>` → 그 스틸을 `out/<이름>/<포맷>/poster.png`로 복사.
- 렌더·검사·포스터가 다 끝난 **뒤에** `node tools/state.mjs films/<이름> stage=deliver waiting=none` (엔진을 고정하므로 검사를 통과한 결과에만).
- 디자이너에게: 완성본이 플레이어 아래 결과물 줄에 있다는 것, 다음에 개선할 점 한 줄. 파일 경로는 말하지 않는다.

## 수정 요청이 오면
메시지 앞의 `▸ 10.86초 · 16x9 · 왼쪽 위 영역 (x 10~35%, y 20~45%)` 줄은 디자이너가 앱의 "고칠 곳 표시"로 감싼 시각·포맷·영역이다(점이면 `(x 22%, y 30%)`, 여러 줄이면 여러 곳). 그 아래 글이 요청이다. 먼저 `node tools/render.mjs films/<이름> --format 16x9 --stills 10.86`으로 그 프레임을 뽑아 그 영역을 잘라 본다. 손잡이(params 슬라이더)로 풀리는 요청이면 값을 바꿔 보여 주고 손잡이로 풀 수 있었다고 알린다.
`index.html` 맨 위의 장면 의도와 상태 표부터 읽고 고칠 곳을 찾는다(코드 전체를 다시 읽지 않는다). 고친 뒤 의도가 바뀌었으면 주석도 고친다.
"3초쯤 토글이 너무 빨라요" → 해당 키의 시각/스프링 프리셋만 바꾸고 `--from 2.5 --to 4.5`로 구간 렌더해서 먼저 보여준다. OK면 전체 렌더.
